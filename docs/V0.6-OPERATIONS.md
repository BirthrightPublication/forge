# V0.6 operations and recovery

## Models and CUDA

Starting transcription authorizes the selected approved Whisper model download.
The old first-download checkbox is retired; its field remains readable in older
presets/history. Model files stay in `%LOCALAPPDATA%\FORGE\models` or the existing
`FORGE_DATA_DIR\models`. FORGE adopts compatible existing snapshots without moving
them and retains selected immutable revisions. Updates offers newer revisions;
older cached revisions stay selectable. Per-model OS locks coordinate processes.
Incomplete or hash-rejected downloads cannot become ready cache entries. Retry
resumes the publisher cache; offline errors list cached alternatives.

CUDA diagnostics distinguish GPU/driver enumeration, DLL loading and actual
inference. The pinned CTranslate2 4.6.0 engine requires CUDA 12 cuBLAS and cuDNN 9;
a driver advertising CUDA 13.2 does not prove those runtime libraries are present.
Official NVIDIA links appear beside diagnostics. No driver or system installer is
downloaded/executed automatically. After installing compatible runtime libraries,
use **Updates → GPU runtime → Diagnose → Test CUDA inference** with a cached model.
That test actually consumes the model's lazy inference generator on local silence.

Auto selects CPU when the runtime is unavailable, reports the decision, and falls
back after a catchable CUDA failure. Explicit CUDA keeps the preference and reports
the repair needed. Known runtime failures stop repeated CUDA dispatch for one hour
or until successful diagnostics/inference. Out-of-memory failures are not cached
as permanently broken runtimes. No physical RTX 5080 has been tested on the Linux
cloud runner; Windows DLL and hardware acceptance must be reported separately.

## Dependencies and maintenance

Updates discovers registered classes and tested requirements, existing locations,
import failures and available compatible versions. Missing optional components are
install choices, not notification counts. Install/Update All explicitly approves
selected dependency classes from PyPI; subsequent controlled repairs can reuse that
approval. New application versions always require another approval.

Existing jobs finish before a requested installation. Cancel the installation request
to keep working; cancel processing jobs separately through the existing confirmed
queue action if needed. Automatically approved repairs preserve queued jobs, let
active jobs finish, pause new dispatch and resume the prior dispatch preference.
When a batch includes both models and environment/application maintenance, model
downloads stay queued until installation verifies the engine and restarts FORGE.
The external host runs from base Python, waits on the server's exact Windows process
handle, and installs only registered wheel requirements. Existing environments are
backed up, compatible wheels are prepared before replacement, and installation runs
without an online package index. `pip check` and imports verify the result. Failure
restores the previous environment and retains diagnostic/backup material. Models
and application data are outside the environment transaction.

The service restarts and the Studio shows the maintenance result. If Windows,
network access, storage or restoration fails, use the existing external installer
or updater and review `%LOCALAPPDATA%\FORGE\maintenance` (or `FORGE_DATA_DIR`).
Environment backups can be large; they are deliberately retained for recovery.
Do not delete them during an unfinished installation.

A durable maintenance marker prevents launching another service during replacement.
If the installer was interrupted, close FORGE, open a command prompt in `B:\Forge`,
and run `py -3 scripts/managed_install.py --recover` with base Python. Recovery
refuses to run beside a live installer, restores the journaled environment backups
and completes any pending application rollback before permitting a normal launch.
Keep the marker and backups if recovery reports an error; do not bypass the guard.

## Updates and private state

Checks run at startup and periodically on a background thread, with bounded HTTPS
requests, cached results and offline retry delays. They never upload media, prompts,
cookies or transcripts and never require an update-service account. Application
checks use `BirthrightPublication/forge`; models use the registered Hugging Face
repositories; Python packages use PyPI within reviewed constraints. FFmpeg/FFprobe,
ExifTool and GPU runtimes remain user-managed with diagnostics rather than unvetted
executable downloads. App installation uses the existing verified legacy manifest
adapter; the separate `app/` Windows asset remains compatible with the installed PS1.

Working settings save automatically and survive restarts independently of named
presets. Generated values, vocabulary text, QR/contact/Wi-Fi content, cookie paths,
metadata text and watermark content are excluded. Output preferences and nonsecret
model/configuration choices are retained. Reset defaults affects working settings,
not presets, queue history or source media.

Execution durations use a monotonic clock and exclude time queued. Stage durations
record actual observed stage transitions; old records without measurements show no
invented duration. Automatic scheduling retains the five-job ceiling, separate
resource budgets, GPU memory admission and serialization of identical GPU models.
A shared in-process model worker was not adopted without a real GPU performance
comparison; process isolation and cancellation behavior are retained.

## Release and rollback

The next approved source tag is `v0.6.0`. Required assets are
`FORGE-v0.6.0-windows-x64.zip` and its `.zip.sha256`, plus validation evidence.
The legacy offline package is `FORGE-v0.6.zip`. Until approval, tag and publication
succeed, these names describe candidates rather than an available public release.

Keep `B:\Forge\Update FORGE.bat`, `Update-Application.ps1`, `Build`, existing
settings/presets/workflows/history, models and both environments. The Windows ZIP
contains only application files under `app/`; it excludes protected updater files
and user data. External updater and legacy rollback safeguards remain available.
The supplied PS1's short-TEMP-path limitation and workaround remain documented in
`WINDOWS_RELEASES.md`; managed FORGE updates use the verified local updater adapter.
